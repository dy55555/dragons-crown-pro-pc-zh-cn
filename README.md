# Dragon's Crown Pro PC · 简体中文界面语言包

给 [saulob/dragons-crown-pro-pc](https://github.com/saulob/dragons-crown-pro-pc) 的 TRG 启动器做简体中文汉化，
**覆盖启动器全部界面**。不改任何功能逻辑、不含游戏本体、不含上游 exe。
官方升级后重新双击一次 bat 就能继续用。

> 覆盖包括游戏内按 **F1 / F10** 呼出的选项与金手指菜单：这两处的内嵌字体
> 也已一并换成中文子集，菜单里的中文可以正常显示。

## 一键汉化

1. 安装 Python 3（Windows 安装时勾选 *Add Python to PATH*）。
2. 把本文件夹放到任意位置；**推荐直接放进游戏安装目录**（和 `dragons_crown_pro.exe` 同级）。
3. 双击 **`一键汉化.bat`**。
4. 正常启动 `dragons_crown_pro.exe`，启动器界面即为简体中文。
   游戏内 `F1` 选项菜单、`F10` 金手指菜单里的中文也已能正常显示。

如果脚本找不到 exe，任选一种：

| 方式 | 操作 |
| --- | --- |
| 拖放（最省事） | 把 `dragons_crown_pro.exe` 直接拖到 `一键汉化.bat` 图标上 |
| 命令行 | `python apply_zh_ui.py --exe "完整路径"` |

> 运行前请先关闭启动器 / 游戏，否则 exe 被占用会写入失败（脚本会明确提示）。

## 官方升级后继续用（重点）

| 情况 | 你要做的 |
| --- | --- |
| 官方更新覆盖了 exe | **重新双击 `一键汉化.bat`**，一次搞定 |
| 更新后多了新设置项 | 新词条先显示英文；往 `zh-UI.tsv` 补一行译文，再跑一次 bat |
| 想确认当前是不是汉化版 | 双击 `检查状态.bat` |
| 想回官方原版 | 双击 `还原官方版.bat` |

升级后还能用，靠的是这几点：

- **按英文原文匹配**，不按行号、不按文件偏移。上游增删词条、重排顺序都不会错位。
- 脚本自动识别「exe 已被官方换成新版」，更新原版备份后重新打补丁；重复运行完全幂等。
- 内置两道保险：动到 Windows 导入表名字就**整批作废并报错**；文字由代码拼装的条目
  会自动连同指令立即数一起改，改不了就保留英文，**绝不写出半个汉字**。

## 改翻译 / 补词条

`zh-UI.tsv` 每行两列，用 TAB 分隔：

```
英文原文<TAB>简体中文译文
```

第一列是匹配用的英文原文，**不要改**；只改第二列。规则：

- 转义：`\s` = 空格，`\n` = 换行，`\t` = 制表符，`\\` = 反斜杠。
- `%s` / `%d` 等占位符必须和英文原文**数量一致**。
- 以 `#` 开头的是注释行。
- 未收录的词条一律回退为英文，不会串出上游自带的葡语。

> **译文要尽量短。** 汉化是「就地替换」，中文占的字节数不能超过英文原文
> （一个汉字 3 字节，通常 10 个汉字 ≈ 30 字节）。超长的条目脚本会列出来，
> 改短后重跑即可。

改完重新双击 `一键汉化.bat` 生效。想贡献译文欢迎提 PR。

## 不影响哪些东西

只改 exe 里的**显示层**，不碰任何逻辑：

| 改动 | 作用 |
| --- | --- |
| `.rdata` 里的英文界面字面量（就地等长替换） | 启动器界面文字换成中文 |
| `.text` 三处内联字体名 + `.rdata` 三份字体名字符串 | Segoe UI → `simhei.ttf`，让启动器中文有字形 |
| ImGui 默认字形范围 `0x20–0xFF` → `0x20–0x9FFF` | 让中文字形被光栅化 |
| 内嵌 `DejaVuSans.ttf` → `zh-overlay.ttf`（就地替换 + 补零到原长） | 让 F1 选项 / F10 金手指菜单的中文有字形 |

**不改**：`user/dcp.ini`（游戏内语言、窗口、显卡、金手指开关一概不动）、存档、
联机 / 好友码、奖杯、金手指逻辑与数值、任何游戏文件（CPK / PKG / eboot）。

### 🔒 内部键保护（关键：绝不能把功能键也译成中文）

有少数英文串**长得像界面文字，实际是代码拿来比较的键**。一旦译成中文，比较就会
永远不成立，功能直接坏掉。脚本用整段上下文锚点识别并跳过它们：

| 受保护串 | 位置 / 用途 | 误改后果（已实际踩过） |
| --- | --- | --- |
| `Cheats` ×3 | 金手指签名表的 `spec.feature`、诊断分类键 | F1/F10 金手指全部失效：`cheat set sites: incomplete`，菜单变「不可用」 |
| `Voice language`（`Cheats` 旁那处） | v1.4.1 新增的同组 feature 分类键 | 破坏语音语言功能的站点筛选 |
| `Direct connections` | 联机连接测试 `connection_test.cpp` 的判断键 | 联机诊断不显示直连问题的解决建议 |
| `Router configuration` | 同上 | 联机诊断不显示路由器配置的解决建议 |

锚点取「紧邻的下一串」而非写死偏移，v1.4.0 / v1.4.1 / v1.5.1 的上下文都保留：
v1.4.1 把三处 `Cheats` 的邻串分别改成了 `hook: damage`（机器码前缀变了）、
`site`+`not a supported game build`（中间多一段）、`Voice language`（原来是
`Japanese NPC voices`）；v1.5.1 这三处邻串结构未再变，**6 处保护直接命中**。
只用旧锚点的话升级后全部落空，`Cheats` 会被译成「作弊」导致金手指全废——
本项目已踩过两次，故 `--check` 会打印保护命中数，升级后必须核对：
正常应为 **6 处**（Cheats×3 + Voice language + 联机×2），少于这个数就是锚点失效信号。

v1.4.0 新增的角色编辑器又带出一组同类词：**六个职业名**
`Fighter` / `Amazon` / `Elf` / `Dwarf` / `Wizard` / `Sorceress`。
`ClassName()` 的返回值既显示在编辑器列表里，又被拼进外观缓存文件名和网络纹理路径
（`PLAYER/FIGHTER0…_NET.ftx`）以及 Boss 战文本键。译成中文会让这些路径/键对不上，
破坏外观同步。因此这六个词**不收进译文表**（保持英文显示），只在编辑器里以英文职业名出现。

> 这也是本项目的血泪教训：曾把 `Cheats` 全部 5 处一律译成「作弊」，其中 3 处是内部键，
> 结果金手指全废。现在同一词的 5 处里只有真正显示的 2 处会汉化，3 处内部键保持英文。
> 配置键（`windowed`/`borderless`/`0`/`1`/`16:9` 等内部值）同样逐处核对过，全部未动。

> 游戏内「菜单与字幕语言」请用启动器那个下拉框自己选，跟本语言包无关。

## 工作原理（简版）

上游启动器是 ImGui + 一层极薄的 C++ 外壳。它的界面文字有两类来源：

1. **`.rdata` 里的英文字面量** —— 侧边栏 `Ui::NavItem("Graphics")` 这类直接写字面量，
   不走 `Tr()` 翻译函数。本语言包就是把这些字面量**就地**换成中文（中文更短，补 NUL），
   所以不需要改任何引用地址、也不用改文件长度或 PE 结构。
2. **运行时由代码拼出来的串** —— 少数文字是「`.rdata` 前 N 字节 + 指令里的 8 字节立即数」
   拼成的，例如 `Check the game files and start` + `"playing."`（后者是 `movabs rcx, imm64`）。
   这类串只改 `.rdata` 会被立即数盖掉，出现「半个汉字 + aying.」。脚本会先扫描
   `movups xmm, [rip+…]` 确认哪些串被整块拷走，再找紧邻的 `movabs` 立即数，
   把中文按同样的切分点分开写进去。

   ★ 拼接点必须**按副本位置分别**记录：同一个词在 exe 里常有多份，通常只有一份是
   拼接的。曾把拼接切分点套到全部副本，导致 `Borderless Fullscreen` 四处全变成
   「无边框全+llscreen」的残串。现在每份副本各按自己的切分点处理，并在末尾统一
   清零残留字节。译文也尽量压到槽长以内，避免依赖立即数。
3. **定点补丁** —— 有少数词通用规则处理不了，用整段上下文做锚点单独修：

   | 词 | 问题 | 做法 |
   | --- | --- | --- |
   | `Play` | 紧贴显示器名尾部（`Generic PnP Moni`+`Play`），「前一个是 NUL 才算串首」的防误改规则会跳过它 | 锚点定位后定点写「玩」 |
   | `About` | 5 字符槽装不下 6 字节的「关于」，通用逻辑会走迁移分支，但导航块没有引用地址可改 | 借用紧邻的空闲 NUL 字节，就地写「关于」，不移动任何字节 |
   | `Russian` | 表里有小写 `russian`（内部语言键，绝不能动）和大写 `Russian`（显示名） | 只改显示名为「俄语」 |

字体是第二道坎。exe 里有**两套各自的 ImGui 上下文**，字体要分别处理，但文字来源其实是
同一批 `.rdata` 字面量（上游 `gpu/shim/dcp_overlay.cpp` 用 `dcp::Tr(...)` 取词，
`launcher/localization/ui_text.cpp` 也用同一个 `Tr()`）——所以文字早就汉化好了，
方块纯粹是「字体里没有对应字形」：

| 渲染 contexts | 谁在用 | 字体 | 处理 |
| --- | --- | --- | --- |
| 启动器 ImGui | 启动器主窗口、各设置页 | `Segoe UI` → 系统黑体 `simhei.ttf` | 改字体名 6 处 + 字形范围 |
| 游戏内 ImGui（overlay） | **F1 选项菜单 / F10 金手指菜单** | 内嵌 `DejaVuSans.ttf` → 中文子集 `zh-overlay.ttf` | 就地替换字体数据 |

启动器的字体名在 exe 里有两种形态，必须都改：`.text` 里三条 `movabs rax,"segoeui."` 内联立即数，
以及 `.rdata` 里三份独立字符串 `segoeui.ttf` / `seguisb.ttf` / `segoeuib.ttf`。

字体名换好还差一道：ImGui 默认只把 `0x20–0xFF` 烘焙进字形图集，中文不在范围内仍是菱形。
把范围数组高界从 `0xFF` 扩到 `0x9FFF`。这是个 **u16 小端数组** `{0x20, 0xFF, 0}`
（字节 `20 00 ff 00 00 00`），要整体写成 `{0x20, 0x9FFF, 0}`（字节 `20 00 ff 9f 00 00`）。
曾只改单个字节得到高界 `0x009F`，现在已修正，`--check` 能识别这种改错。

**F1 / F10 菜单是另一套独立字体。** 上游用汇编 `.incbin` 把 `DejaVuSans.ttf`（759676 字节）
原样嵌进 exe，`AddFontFromMemoryTTF` 加载；这个字体只有拉丁/西里尔字形，没有汉字。
本工具把随包的 `zh-overlay.ttf`（从**微软雅黑**按全部译文字符做的精简子集，435124 字节）
**就地写回原位置**，尾部补零到 759676 字节——不动任何指针和偏移。
三重校验（字体头签名 + 原长度 + 紧随其后的 `18.0f` 立即数）确保只改这一处、不会误伤。

字体收录：全部译文汉字 + ASCII + 三个关键符号：

| 符号 | 码点 | 用途 |
| --- | --- | --- |
| `‹` `›` | U+2039 / U+203A | F1 选项菜单里左右切换取值的箭头（`‹ Windowed ›`） |
| `·` | U+00B7 | 在线页 /「不兼容」提示的分隔点 |

> 一开始用的是 `simhei.ttf`，但它**没有** `‹ ›` 字形，菜单里那两个箭头会变成 `?`。
> 换用微软雅黑后解决 —— 需要重做字体时跑 `python build_overlay_font.py` 即可，
> 别改回 simhei。`--check` 会显示这套字体的当前状态。

## 存档编辑器（SAVE0.DAT）

附赠一个独立的存档编辑器，改装备/金币等，**已实机验证有效**。

### 用法

双击 `存档编辑器.bat`（需要带 tkinter 的官方 Python 3；bat 会自动挑一个）。
**编辑前先完全退出游戏。** 左侧树每个 DATA slot 下有三个上级分组：**[玩家]**、**[伙伴]**、**[通用道具箱]**（外加 [尾部 18 格]）：

* **[玩家]**（0–15）：自建角色，每人列 **9 套行囊**。角色不是「主装备/备用装备」两套，而是最多 9 套配置（行囊1/2 主力，3–9 备用）；
* **[伙伴]**（16–45）：跟着你的伙伴，实测**只有行囊1有东西，2–9 全空**，所以伙伴节点只列行囊1，不再显示 9 个空行囊；
* 点「行囊N」这一层，右侧列出该套 10 个格子，每格都有【编辑】按钮；
* 点具体 `[n]` 格子：装备可改物品ID、品质词条 1-8、装备等级、攻击力、耐久；道具可改效果ID（换哪件道具）和数量；
* 点角色节点可改等级/HP/技能点，另有只读的人物状态候选值；
* 点 DATA 节点下的 **[通用道具箱]** 可改该存档 500 格共用道具箱（可写 0–498）：点某格的【编辑】改装备（物品ID/词条/等级/攻击/耐久）或道具（效果ID/数量）；
* 点 DATA 节点下的 **[尾部 18 格]** 可看/改 slot 末尾那 18 格消耗品（用途待证实，见下文）。

### 技能为什么不提供修改

游戏对技能/技能点有严密保护：技能等级不在角色的简单字段里（曾怀疑记录 `+0x140` 那 24 字节，实测改掉后进游戏毫无变化），剩余技能点即使改高，进游戏也会按角色等级和已完成任务重算回来。所以编辑器**不提供技能修改**，只保留技能点的显示（改它同样会被重算，仅作查看）。

**三个编辑上的便利：**

1. **每个【应用】旁边都有一个【还原】按钮** —— 只撤销这一格字段的未保存改动，其他改动不受影响。手抖填错直接点还原，不用重新打开存档。
2. **词条格子支持模糊匹配** —— 在词条格里别填数字，直接打中文，比如打「攻击」，下方立刻列出名字带「攻击」的所有词条ID和名称，点一条就自动把ID填进去。简繁通吃（打「攻击」也能搜到「攻擊」），空格分隔可搜多个词，例：`攻击 伤害`。
3. **物品可以搜、也可以手填** —— 物品下拉是游戏全部 302 件装备（`0x00BB`–`0x01E8`，连续无空洞），
   末尾另有一项「道具」（物品ID 恒 `0x70`＝「可堆叠道具」这个条目，具体是哪件看词条1 的效果ID）；嫌翻着累就在「搜装备」里打名字
   （也支持简繁），或者直接「手填ID」填任意十六进制值。

点「保存改动」。保存时自动备份原档为 `SAVE0.DAT.editor-bak`，重算 CRC32 并校验通过才写盘。

命令行也能用：

```
python save_editor.py list                                   # 列出所有角色与装备
python save_editor.py set-item --slot 0 --char 0 --bag 0 --slot-idx 0 --id 0x105
python save_editor.py set-qty  --slot 0 --char 0 --bag 0 --slot-idx 5 --qty 20
python save_editor.py set-mod  --slot 0 --char 0 --bag 0 --slot-idx 0 --index 0 --id 0x103
python save_editor.py set-stat --slot 0 --char 0 --bag 0 --slot-idx 0 --field durcur --value 2000
python save_editor.py set-stat --slot 0 --char 0 --bag 0 --slot-idx 0 --field level --value 40
python save_editor.py set-gold --slot 0 --value 12345678
python save_editor.py set-companion --slot 0 --index 0 --level 99 --hp 999 --skill 10   # 伙伴1
python save_editor.py set-companion --slot 0 --index 0 --name "MyHero"                  # 改名字(ASCII 1-8字符)
python save_editor.py set-box --slot 0 --index 9 --field level --value 40        # 道具箱第10格装备等级
python save_editor.py set-box --slot 0 --index 9 --mod-index 0 --mod-id 0x21      # 改第1条词条
python save_editor.py set-box --slot 0 --index 9 --item 0x105                    # 换成十字军之弓
python save_editor.py set-box --slot 0 --index 1 --qty 99                        # 消耗品格数量
python save_editor.py set-pouch --slot 0 --index 0 --kind 0x190 --qty 9          # 尾部18格第1格换成陨石卷轴x9（效果ID=0x190）
python save_editor.py search-mod 攻击                                             # 模糊查词条ID（简繁通吃）
python save_editor.py search-mod "攻击 伤害" --limit 20                            # 多个关键字同时命中
```

`--bag` 取 `0–8`，对应界面的「行囊1–9」；`--index` 在 `set-pouch` 里是 `0–17`，在 `set-companion` 里是伙伴号 `0–29`。

界面上 DATA 节点下有三个上级分组：**[玩家] N/16**、**[伙伴] N/30**、**[通用道具箱]**。玩家和伙伴都点分组看总览、点单个改等级/HP/技能点，展开行囊改装备——全部复用同一套编辑逻辑。区别：玩家列 9 套行囊，伙伴只列行囊1（2–9 实测全空）。命令行改装备用
`set-item/set-mod/set-stat --char 0..15`（玩家）或 `--char 16..45`（伙伴，16=伙伴1，38=伙伴23）。

### 已搞清的存档结构（CUSA10209 1.00 Asia/HK）

| 项 | 偏移 / 值 |
| --- | --- |
| 文件大小 | `0x20EB18`，固定 |
| 文件头 | `0x00` = u32 CRC32（覆盖 `[4, EOF)`，标准 IEEE 反射多项式 `0xEDB88320`）；`0x04` = `DCSD` |
| DATA slot | 3 个，stride `0xAF8D4` |
| 金币 | slot 基址 + `0xAF288`，u32 小端 |
| 角色记录 | slot 基址 + `0xA400` + 记录号 × `0x21D0`。**0–15 = 自建角色，16–45 = 伙伴，46–75 = 待复活遗骸**，三段同构、共用一套字段 |
| 角色字段 | HP `+0xDC/+0xE0`、技能点 `+0xF4`、等级 `+0xF6`(u8, 存值=显示−1)、职业 `+0xF7`、名字 `+0x208`(8字节，另有副本 `+0x210`) |
| **9 套行囊** | 角色基址 + `0x288` + 行囊号 × `0x354`（行囊号 `0–8`），每套 10 格 × `0x54` 字节；`0x354 = 10×0x54 + 0x14`。旧的「备用栏 `0x5DC`」其实就是第 2 套起点 |
| **通用道具箱** | slot 基址 + `0x100`（DATA1=`0x100`/DATA2=`0xAF9D4`/DATA3=`0x15F2A8`），**500 格 × `0x54`**，结构同行囊装备：物品ID在槽首、词条在 `-0x40`、等级 `+0x0E`、攻击 `+0x10/11`。占用看 `+0x00` 是否非 0。类型标记 `+0x02`：`0x2A00`=箱中装备、`0x2200`=消耗品、`0x2800`=法杖、`0x2C00`=素材、`0x2000`=空（高位置 `0x8000` 是标志位，判类型前先 `& 0x7FFF`）。该 slot 内所有角色共用 |
| **物品ID** | 每格首 2 字节，u16 小端，范围 `0x00BB`–`0x01E8` |
| **slot 末尾 18 格** | slot 基址 + `0xAF2D4`，**18 格 × `0x54`**，全是消耗品（物品ID 恒 `0x0070`、类型标记 `0x2200`）。DATA1 满格、DATA2 17格、DATA3 全空。**游戏内找不到对应界面，归属待证实** |
| **道具（消耗品）** | 物品ID `+0x00` 固定 `0x0070`（＝「可堆叠道具」这一个基础条目，不是种类）；`+0x0C` 的**低字节** = 数量（实测 x20/x8/x4/x7 全部吻合）；**词条槽 1 = 效果ID**，真正区分是哪件道具靠它。数量 `0xFF` 表示不可堆叠的特殊物品 |
| **词条槽** | 在物品ID **往前 `0x40`** 处，8 个槽 × 8 字节：u16 词条ID + u16 flags + f32 参数；`0xFFFF` = 空槽 |
| **品质** | 由生效词条数决定：`E`=0、`D`=1、`C`=2、`B`=3、`A`=4、`S`=5（实测 A级猎人之弓 4 条、S级预言坠饰 5 条） |
| **装备等级** | 物品ID `+0x0E` u8，显示等级 = 存值 + 1（实测 `0x22` → LV35） |
| **攻击力/数值** | 物品ID `+0x10`/`+0x11` 两个 u8；武器是 ATK 上下限（弓 `0x56/0x60` → 86-96；长弓 `0x5C/0x5F` → 92-95） |
| **耐久** | 物品ID `+0x04`/`+0x08` u32，显示值 = 存值 ÷ 100（195889 → 1958） |

### 角色 / 伙伴 / 遗骸：同一条数组的三段

`slot基 + 0xA400` 起有一条步长 `0x21D0` 的大数组，**角色、伙伴、遗骸都排在里面**，字段布局完全一样
（HP、等级、职业、名字、9 套行囊全都能照搬）：

| 记录号 | 是什么 | 编辑器 |
| --- | --- | --- |
| 0–15 | 自己建的角色（DATA1 实占 0–1：Natalia、Dinah） | 可编辑 |
| 16–45 | **伙伴**（DATA1 实占 16–38 共 **23 个**：Shauna…Glen） | 可编辑 |
| 46–75 | **路上捡到的遗骸**，要在教堂复活才会变成伙伴 | **不开放**（一哥 2026-11-23 确认） |

伙伴 = 绝对记录号 `16 + 伙伴号`，所以命令行改伙伴装备写 `--char 16`（伙伴1 Shauna）到 `--char 38`（伙伴23 Glen）。

**判定伙伴存在的坑**：不能直接用 `present()`——伙伴1 Shauna 的记录头 `+0x00` 恰好是 `0xCCCCCCCC`，
会被当成空格漏掉，23 个就只剩 22 个。这里改用「名字首字节非 0」判定（`companion_present()`），
实测 23 个全中，DATA2 是 23 个（旧备份），DATA3 是 0 个。

### 关于「备用装备」其实是 9 套行囊

角色并不是只有「主装备 / 备用装备」两套。实测每套起点是 `角色基址 + 0x288 + 行囊号×0x354`，
行囊号 `0–8` 共 9 套，每套 10 格。以精灵 Natalia 为例：行囊1 = 猎人长弓/预言坠饰/守护者之靴…，
行囊2 = 长弓/王室护身符/皮靴…，行囊3–9 = 备用短弓/皮制披风。
旧的「备用栏 `0x5DC`」正好是 `0x288 + 0x354`，也就是第 2 套；而更早的 `0x630` 是第 2 套的第 2 格，会漏掉第一件。

### 通用道具箱（真正的仓库，500 格）

每个 DATA slot 从 `slot基 + 0x100` 起是道具箱，结构和行囊装备完全相同
（物品ID在槽首、词条在往前 `0x40`、等级/攻击/耐久字段一致），是**该存档所有角色共用**的仓库。
DATA1=`0x100`、DATA2=`0xAF9D4`、DATA3=`0x15F2A8`。

**格数就是 500，和游戏界面写的一致。** 这是量出来的物理边界，不是猜的：
空槽 DATA3 里从 `slot+0x100` 起恰好是 **500 条**全空记录，第 501 条起点 `slot+0xA510` 开始整段变全零。

```
slot+0x100 + 500 × 0x54 = slot + 0xA510   ← 500 条记录到此为止，之后全是 0x00
500 × 0x54 = 0xA410 字节，远小于 slot 长度 0xAF8D4，完全放得下
```

> **【早期错误，已纠正】** 之前把箱底写成 `0xAD8`，比真正起点晚了 `0x9D8`，正好 **30 格**。
> 由此连锁出三个错结论：① 漏掉最前面 30 格里的 30 件物品；② 尾部越界多读 30 格；
> ③ 于是数出「466 格 / 312 件」。
> `0xAD8` 不是任何结构的起点，它只是「旧基点 + 235 × `0x54`」这个巧得离谱的位置。

**占用判定（关键）**：看每格的**物品ID `+0x00`**，`!= 0` 就算占用。

不能用类型标记 `+0x02` 判——箱里有 2 件装备的类型标记也写成了 `0x2000`
（索引 4 = `iid 0x01C3` 熊脚靴、索引 27 = `iid 0x01C9` 衝擊披風，三个 DATA 里完全一致）。
按类型判会漏掉这 2 件：

| 判据 | DATA1 数出来 | 说明 |
| --- | --- | --- |
| `typ(+0x02) != 0x2000` | 340 | 漏掉 2 件误标装备 |
| `iid(+0x00) != 0` | **342** | 与游戏界面一致 |

游戏界面读数是 **342**；把遗忘灵药用掉之前是 **343**。这两个数正好差 1，与物品ID 判据逐位吻合，
所以判据确定无疑。顺带一提，DATA2（上一代备份）是 301 件，DATA3（空槽）是 0 件。

类型标记含义：`0x2A00`=箱中装备、`0x2200`=道具、`0x2800`=法杖、`0x2C00`=素材、`0x2000`=空。
最高位 `0x8000` 是标志位（疑似「新物品/未读」），判类型前要先 `& 0x7FFF`：
实测量到过 `0xA200`（= `0x2200 | 0x8000`）的治愈药水，和 `0x2200` 是同一类东西。

**索引 499 不可写**：它虽然是第 500 格，但 `0x54` 字节已经压在角色0 的记录头上
（`0xA4BC + 0x20 = 0xA4DC` 正是角色0 的血量字段）。角色0 记录开头约 `0xD0` 字节是保留区
（与空记录模板逐字节相同），所以 0–498 写进去不会伤到角色；499 会。编辑器因此只开放 **0–498**。

> 判断「是不是道具」**不能只看类型标记 `0x2200`**：实测有 3 件装备（`0x181` 勇敢錬坠、
> `0x186` 寶石護身符、`0x1BF` 駝色靴）类型标记也是 `0x2200`，但字段结构完全是装备。
> 可靠判据是 `+0x00 == 0x0070`。

### slot 末尾那 18 格：到底是什么还没证实

每个 DATA slot 末尾还有一块 18 格容器：`slot基 + 0xAF2D4`，格宽同样是 `0x54`。
DATA1 满 18 格、DATA2 用 17 格、DATA3 全空。

里面的东西看着完全是玩家的消耗品——抗性药水、坚毅之魂、强效药剂、幸运药水、炸药、
陨石/暴风雪/重生/强酸卷轴、炽炎/烈焰/剧毒戒指，数量零散，很像精心准备的出击套装。

**但它在游戏里找不到对应的界面。** 逐个比对了「效果ID」：DATA1 那 18 格**全部**不在道具箱里，
DATA2 只有 2 格（治愈药水小、治愈戒指）能在箱里找到同款。所以它不是道具箱的镜像或缓存，
也不是什么「随身携带的道具」——早期那个名字是想当然，现在只按「尾部 18 格」中性呈现。

**为什么只取 18 格**：`0xAF2D4 + 18×0x54 = 0xAF8BC`，距 slot 末尾 `0xAF8D4` 只剩 `0x18` 字节。
若按 20 格取，第 19、20 格的起点 `0xAF910` 已跨进下一份 DATA，写下去会改到别的存档位。

### 全部物品格：一共 1958 格

| 容器 | DATA1 起点 | 格数 | 说明 |
| --- | --- | --- | --- |
| 角色行囊 | `0xA400 + 角色×0x21D0 + 0x288 + 行囊×0x354` | 16 角色 × 9 套 × 10 格 = **1440** | 装备 / 防具 / 饰品 / 消耗品 |
| 通用道具箱 | `0x100` | **500** | 该 slot 所有角色共用，可写 0–498 |
| 尾部 18 格 | `0xAF2D4` | **18** | 用途待证实 |

合计 `1440 + 500 + 18 = 1958` 格，每格都是 `0x54` 字节、同一套结构。
为确认没漏，把 DATA1 整段按 `0x54` 对齐扫过一遍：角色记录之后到尾部 18 格之间的
537044 字节里，命中已知物品类型的格子只有 7 个且不成片，没有第四块物品容器。

### 装备ID是连续的 302 件，按 40 件一组排

`save_items.tsv` 里 `0x00BB`–`0x01E8` 共 **302 条，逐号连续、没有空洞**（302 = 488−187+1）。
游戏数据表按每组 40 件排：`0x0BB/0x0E3/0x10B/0x133/0x15B/0x183/0x1AB` 各 40 件（7 组），
最后 `0x1D3`–`0x1E8` 是 22 件（手套、眼镜这一批）。
组内混着不同品类（剑和斧会在同一组、弓和锤会在同一组），所以别拿 ID 段当类型用。

### 物品记录是两层结构：`+0x00` 定种类，词条槽 0 定具体是哪个

这条最容易搞错，先说结论：**存档里所有道具的 `+0x00` 都是 `0x0070`，但 `0x70` 不是「种类」，
只是「一个可堆叠道具」这个基础条目。真正区分是哪件道具的，是词条槽 0 里的效果ID。**

| 层 | 位置 | 装备 | 道具 / 技能 |
| --- | --- | --- | --- |
| 基础物品ID | `+0x00` | 每件一个，`0xBB`–`0x1E8` 逐号连续 | **全部固定 `0x0070`** |
| 具体是什么 | 词条槽 0（`物品ID − 0x40`） | 词条ID `0x20`–`0x11C` | 效果ID `0x17F` 起 |
| 在哪个容器 | `+0x02` | `0x6800` 行囊武器 / `0x6A00` 行囊防具 / `0x2A00` 箱中装备 / `0x2800` 法杖 | `0x2200` |

两段编号**永不重叠**，这一点用存档实测过：本机存档里装备用到的词条最大 `0x11C`，
道具用到的效果最小 `0x17F`。所以同一个 u16 字段在两种物品里没有歧义。

效果ID 的段位（依据：游戏文本表 `CustomItem` 的条目顺序，逐条核对得来）：

| 段位 | 内容 | 例子 |
| --- | --- | --- |
| `0x017F`–`0x018D` | 戒指：火 / 冰 / 雷 / 毒 / 治疗，**各三档** | `0x17F` Fire Ring 火焰 → `0x180` Flame 烈焰 → `0x181` Blaze 炽炎 |
| `0x0190`–`0x0194` | 卷轴 | `0x190` 陨石卷轴、`0x193` 强酸卷轴、`0x194` 重生卷轴 |
| `0x0197`–`0x01B4` | 药水，每类强度三档连排 | `0x19D/19E/19F` = 抗性药水 小/中/大 |
| `0x01B6`–`0x01CF` | 符文石 Runestone **A–Z**（26 个） | `0x1B6` 符文石 A |
| `0x01D1`–`0x01F8` | 技能道具：各职业技能 + 法术（40 个，只读） | `0x1DA` 淬毒锐锋、`0x1E9` 法术：陨石群 |
| `0x01FA`/`0x01FB` | 特殊/任务道具 | `0x1FA` 魔眼灵魂捕捉瓮、`0x1FB` 亚马逊仪式护甲 |
| `0x0209`/`0x020A` | 特殊道具 | **`0x209` 遗忘灵药（洗点）**、`0x020A` 征服者印章 |

段与段之间夹着几条「…判定用」的占位条目（`0x18E` 戒指判定用、`0x18F`/`0x195` 卷轴判定用、
`0x196`/`0x1B5` 药水判定用、`0x1D0`/`0x1F9` 技能判定用、`0x1FD`/`0x207` 背包判定用），
它们不是真道具，别当名字用。

### 道具真名怎么来的：文本表下标 = 效果ID + 0x749

汉化工程里那份 `_upstream_en_CustomItem.json` 就是游戏文本表（`CustomItem` sheet）的英文原文，
共 5238 条。它的条目顺序和存档里的效果ID 差一个固定偏移：

```
文本表下标 = 效果ID + 0x749
```

用六条互相独立的记录验证，全部吻合：

| 存档效果ID | +0x749 | 文本表原文 | 是不是这件道具 |
| --- | --- | --- | --- |
| `0x190` | `0x8D9` | Meteorite Scroll | ✅ 陨石卷轴 |
| `0x1A3` / `0x1A5` | `0x8EC` / `0x8EE` | Strong Draught (S) / (L) | ✅ 强效药剂 小/大 |
| `0x1A9` | `0x8F2` | Stalwart Spirits (S) | ✅ 坚毅之魂 小 |
| `0x1AC` | `0x8F5` | Blood of the Ogre (S) | ✅ 食人魔之血 小 |
| `0x1AF` | `0x8F8` | Liquid Luck (S) | ✅ 幸运药水 小 |
| `0x1FB` | `0x944` | Ritual Amazon Armor | ✅ 亚马逊仪式护甲 |

**重要教训：中文词条表（`save_mods.zh.tsv`）在 `0x17F` 之后那段是错的，不要拿它当道具名。**
同一批下标，英文原文是形容词（`0x190` = `Sapper's`、`0x19E` = `Dragon's`、`0x1FB` = `Despairing`），
中文表却写成「從天空降下大量火球雨」「免疫異常狀態，持續60秒」——把「效果描述」塞进了「名字」的位置，
还整体错了一位（`0x19E` 一度被当成抗性药水（小），实际是（中））。`0x0000` 附近两表一致，越往后越偏。

所以道具名一律以文本表 + `0x749` 为准，`save_consumables.tsv` 按这个规则生成（现 116 条，覆盖全段）。

### 遗忘灵药（洗点道具）

`0x0209`，文本表里写作 `##(SKILL_RESETITEM)`（宏，游戏运行时展开成「遗忘灵药」）。
它在游戏里是特殊道具，不是药水，存储结构和别的道具一样：`+0x00 = 0x0070`、`+0x02 = 0x2200`、
词条槽 0 = `0x0209`，数量写 `0xFF`（表示不可堆叠，界面不显示件数）。

作用：重置该角色所有技能点（`Deep Pockets` 除外），要在冒险者公会使用，用完消失。
正常玩法里只在混沌迷宫第 3/6/9/99 层首次通关时各给一个。

### 网上资料交叉验证（重要旁证）

PS3 原版《Dragon's Crown》（`BLUS30767`）的存档偏移与这部 PC 移植版**完全一致**：

| 用途 | PS3 社区代码页 | 本工具实测（PS4/PC 存档） | 结论 |
| --- | --- | --- | --- |
| DATA1 金币 | `0x000AF288` | `0xAF288` | ✅ 一致 |
| DATA2 金币 | `0x0015EB5C` | `0xAF8D4 + 0xAF288 = 0x15EB5C` | ✅ 一致 |
| DATA3 金币 | `0x0020E430` | `2×0xAF8D4 + 0xAF288 = 0x20E430` | ✅ 一致 |
| 角色1 格1 词条1 | `0x0000A648` | `0xA400 + 0x288 − 0x40 = 0xA648` | ✅ 一致 |
| 角色 stride | 代码里 `401021D0` 的重复填充 = 步长 `0x21D0` | `CHAR_STRIDE = 0x21D0` | ✅ 一致 |

也就是说这套偏移不是这一次逆向猜出来的，第三方 PS3 存档代码独立印证了同一组数字。
参考来源：

* `save-editor.com` — BLUS30767 Dragon's Crown SAVE EDITOR CODE（金钱/技能点/等级偏移表）
* NextGenUpdate — Dragon's Crown Item Editor 帖（`0xA648` 起 8 个词条槽、`0x43FF` 参数、CRC 必须重算）
* GameFAQs — Dragon's Crown Pro Guide（装备分品类名：Rods/Hammers/Swords/Gauntlets/Shields/Belts/Amulets/Gloves/Glasses）
* Dragon's Crown Wiki — Equipment Properties（各职业每层固定装备词条）

装备名与词条名的中文，是照这份 xlsx + 日式游戏词库惯用译法直译的，不是官方译名。

> 早先误当成「道具箱」的 `slot基 + 0xAF2D4` 起那 18 格是另一块独立容器，用途未证实，不是仓库。

### 行囊里的「技能道具」为什么只读

这里说的是**装在行囊格子里的技能道具**（效果ID `0x1D1` 起的那种）。

上游 `dcp_cheats.h` 里 `IsSkillItem()` 给出官方判定：道具的第一个词条（效果）ID 落在 `0x1D1–0x1F8`
且命中掩码 `0xE362E5F7FF`，就是「技能道具」。掩码 40 位正好覆盖 `0x1D1–0x1F8`，
实测这一段全部是技能/法术，没有遗漏。注意 `0x1FA`/`0x1FB` 是**任务道具**（魔眼瓮 / 仪式护甲），
`0x209` 是遗忘灵药，都不在技能段，以前误把 `0x1FB` 当技能是错的，已纠正。
技能是装在行囊格子里、靠技能点上限制约的，
随意改写会造成技能点与装备不匹配，所以编辑器**只标注 `[技能]`、不开放修改**。

### 「洞察的 / 蛇眼的」这类前缀在哪

**结论：前缀不是独立字段，改不了、也没必要改。** 三条实测证据：

1. 「洞察的」= `Cerebral`、`蛇眼的` = `Serpent-eyed` 这类前缀ID（`0x412`、`0xAFC`…）在整个角色记录里 **0 命中**；
2. 物品头 `+0x0C` 对装备恒为 `0x0100`，也不是前缀；
3. 英文表里 `Pristine / Valkyrie's / Cerebral / Sage's / Branding` 这些「形容词」恰好是**词条ID**
   （预言坠饰的 5 个词条就是 `0x103/0xE7/0x11A/0x112/0x106`）。

也就是说，游戏是按装备身上的词条组合**动态生成显示名**（前缀 + 装备名）的。
你给的 xlsx 中文表把这些「形容词型」词条ID误标成了效果（如把 `0x103 Pristine` 写成「免疫中毒」），
所以中文名和游戏对不上——但改词条就改了属性，前缀显示会自动跟着变，不存在单独的「洞察的」地址。

### 词条数值：为什么表里 +30% 游戏却显示 +10%

**存档里只存「词条类型ID」和「一个 f32 参数」，不存最终显示数值。** 每个词条槽 8 字节：
`u16 词条ID + u16 flags + f32 参数`。以「洞察的狙击弓」为例：

| 词条ID | 存档 f32 参数 | xlsx 表里的文字 | 游戏实际显示 |
| --- | --- | --- | --- |
| `0x21` 伤害 | `34` | 造成的伤害+30% | +10% |
| `0x2B` 击退 | `34` | 攻击的击退值+50% | +16% |
| `0x6D` LUC | `26` | LUC+40 | +10 |
| `0x47` 箭矢 | `14` | 变换场景时箭矢+1 | +1 |

上游 `CustomItem.json` 的英文原文是 `+%d％` 这种**占位符**，数值由游戏按 f32 参数经内部公式（词条ID相关，
不同词条系数不同）现算出来。你给的 xlsx 表把占位符填成了**某个存档的样本数值**，换个版本/装备自然对不上。
攻击力同理：存档狙击弓存 `210`，游戏显示 `201`——显示值是内部换算结果，不是那个字节的原值。

所以编辑器里词条那一列**直接显示词条中文名**，不把 xlsx 的数值当准。改词条只需改 ID 或参数字节，
游戏会自己换算显示。

### 人物状态字段

上游源码确认：人物属性（力量/体力/智力/幸运等）是由**职业 + 等级查表重算**的（`write_stats`），
`SAVE0.DAT` 里**没有独立的 STR/VIT/INT/LUC 字段**。角色记录 `+0xE4..+0xF2` 有 8 个随等级增长的 u16
（Lv65 精灵是 `[300,300,150,152,171,200,123,141]`），含义未最终标定，编辑器**只读展示、不开放修改**。
想调属性请改等级（游戏会按表重算）。

词条槽的位置以前读成「物品ID 往后 `0x14`」，那其实读到了**下一件装备**的词条——所以两件装备都被显示成 5 条。
正确位置是「物品ID 往前 `0x40`」，错开整整一格，实测弓 4 条、坠饰 5 条，与游戏一致。

物品ID对照表见 `save_items.tsv`（从你给的 xlsx 提取）；词条ID见 `save_affixes.tsv`。
xlsx 里的 `DEX`/`SW` 两列是同一16位ID的大小端两种读法，本工具按小端（`DEX`）解读，实机验证正确。

改装备时**只改物品ID这 2 字节 + 重算 CRC**，装备块里其余字节（耐久、词条、外观等）原样保留。
实测把「猎人之弓 `0x100`」改成「十字军之弓 `0x105`」、金币改成 `12345678` 后进游戏，
两者都生效。

> 换职业不匹配的武器（如战士拿法杖）游戏可能忽略或显示异常，建议换同类别物品。
> 词条中文名按「xlsx 中文表优先，其余照日式游戏惯用译法直译」处理（`build_mod_zh.py` 可重建），
> 先保证意思对；数值差得多的（例如表里 +30%、游戏里 +10%）以后逐条改 `save_mods.zh.tsv` 即可，
> 不用改程序。改 ID 本身是安全的。
> 存档格式针对 CUSA10209 1.00 亚洲/港版；其它构建未验证。改前备份，风险自负。
